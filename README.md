# TabEHR

An OHDSI study package. It ports the record preprocessing of the MedRep study
(`create_trajectory.py`) from pandas to SQL, splits the patients once into a
pretraining and a downstream group, derives the measurement bins from the
pretraining patients only, and runs the SparseArray study package restricted to
the downstream patients, so the task inputs and labels never see a patient the
model was pretrained on.

- Why, and every decision already made: [CLAUDE.md](CLAUDE.md)
- Open questions and the default in force for each: [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md)

The database is never reached from a development machine: the code is written
here, you run it. Every check is part of the package, and every result is
appended to `output/<databaseId>/validation_report.md`.

## Layout

The usual HADES layout, as in SparseArray, PatientLevelPrediction and
CohortMethod.

```
R/                     the stages, one file each
inst/sql/sql_server/   OHDSI SQL, rendered and translated by SqlRender
inst/settings/         the analysis settings that are the same at every site
man/                   generated by roxygen2
extras/CodeToRun.R     the runner: connection, schemas, execute()
extras/Check*.R        development checks that need no database
tests/testthat/        the tests, with fixtures produced by pandas itself
SparseArray/           the SparseArray package, with six changes (below)
DockerImage/           the image: the SparseArray stack plus PatientLevelPrediction
```

| File | Holds |

## Running it

```bash
cd /path/to/TabEHR
cp .env.example .env                 # fill in, then: set -a; . ./.env; set +a
R CMD INSTALL SparseArray            # createCohorts() reads its SQL from the installed package
R CMD INSTALL .
Rscript extras/CodeToRun.R
```

`extras/CodeToRun.R` is the only file that knows anything site specific. Copy it
and edit the connection, the schemas and `databaseId`; the analysis settings
come from the package.

It runs with `samplePersonCount = 1000` first. Read
`output/mimic/validation_report.md`, then switch to `createAnalysisSettings()`
with no sample and run it again. The sample has to change before
`extractRecords()`, not halfway through, because every table is rebuilt from the
patients it admits.

An external validation site changes two things and nothing else:

```r
analysisSettings <- createAnalysisSettings(
  quantileSettings = createQuantileSettings(
    basis = "file",
    quantileFile = "output/mimic/meas_quantiles.csv"
  ),
  siteRole = "external"
)
```

## The stages

| Stage | Function | Tables | Files |
|---|---|---|---|
| check | `checkDatabase()` | – | report sections on packages, the BIGINT round trip, the person_id range, write permission, the measurement columns, the vocabulary version |
| 1 | `extractRecords()` | `records`, `measurements`, `concept_unit`, `record_counts` | – (study population criteria only, see below) |
| 2 | `createStudyPopulation()` | `admission_history`, `study_population` | `study_population_flow.csv`, `study_population.csv` |
| 3 | `createPersonSplit()` | `person_split`, `downstream_person` | `person_split.csv`, `split_summary.csv` |
| 4 | `createAllRecords()` | `allrecords_cohort` | `allRecordsCovariates.zip`, `allrecords.csv.gz`, `allrecords_cohort.csv`, `measurementValueUnitRef.csv` |
| 5 | `createTaskInput()` | the cohort table, `plpData/` | `outcomeLabels.csv`, `taskInput/<extraction>/input.csv.gz`, `longFormat/<extraction>/*`, `CohortCounts.csv`, `cohort_counts_restricted.csv` |
| 6 | `extras/CreateMedRepFiles.R` | – | `MedRep/{allrecords.csv.gz, meas_quantiles.csv, train_id.csv, valid_id.csv, test_id.csv, README.md}` |
| check | `runDiagnostics()` | – | `validation_*.csv` and the report |

Every table lives in `cohortDatabaseSchema` under `tablePrefix`, see
`getTabehrTableNames()`. CDM tables are only ever read.

The order is forced by one dependency chain: the study population needs the
record counts, the split needs the study population, and the quantiles need the
split. That is why the bins are applied at the end rather than while the records
are extracted. It is only sound because the bin suffix cannot change a patient's
record count, which `CountRecords.sql` explains and `runDiagnostics()` verifies
against the data.

## Outputs

Everything is CSV (`arrow` is not in the image), `person_id` is always text,
dates are `YYYY-MM-DD` and timestamps `YYYY-MM-DD HH:MM:SS`.

| File | Notes |
|---|---|
| `study_population_flow.csv` | cumulative counts in the order of the criteria, plus the single-criterion counts |
| `study_population.csv` | `person_id`, `n_records`, `n_admissions` |
| `person_split.csv` | `person_id`, `stage`, `split`, `split_seed`: the one source of truth for every later stage |
| `split_summary.csv` | group sizes and fractions, with the overlap check |
| `allrecords.csv.gz` | **the reference data**: `person_id`, `domain`, `concept_id`, `record_date`, `value_as_number`, `unit_concept_id`. Raw values, no bins |
| `allrecords_cohort.csv` | `row_id` to `person_id`, and the index date every `record_date` was reconstructed from |
| `taskInput/<extraction>/input.csv.gz` | `allrecords` cut to one extraction's rows and observation window, with `row_id` and `time_id` |
| `MedRep/*` | the MedRep comparison files, written by `extras/CreateMedRepFiles.R`. `meas_quantiles.csv` is keyed on `(measurement_concept_id, unit_concept_id)`; the deviations from the original are in `MedRep/README.md` |
| `longFormat/<extraction>/` | `featureExtractionLong.csv`, `covariateRef.csv`, `timeRef.csv`, `analysisRef.csv`, unchanged in format |
| `outcomeLabels.csv` | one row per target cohort entry per task: `rowId`, `subjectId`, the cohort dates, the time at risk, the label |
| `cohort_counts_restricted.csv` | cohort sizes after the downstream restriction |
| `run_info.json` | settings, seed, vocabulary version, package versions, timestamp. No credentials |
| `validation_report.md` | appended by `checkDatabase()` and `runDiagnostics()` |

`outcomeLabels.csv` is what the later Python stages consume. A row exists for
every target cohort entry that survived that task's PLP population criteria, so
an entry missing for a task was excluded by them, and
`outcomeLabelsAttrition.csv` says at which step. One patient keeps one row per
admission, which is what lets the evaluation train on all admissions and pick
one admission per patient for validation and test.

## Changes to SparseArray

All changes are applied to both copies: the original repository at
`C:\git\SparseArray` and the copy in `TabEHR/SparseArray`, which are byte
identical on every file git tracks. Cohort definitions, covariate settings,
population settings and output formats are untouched; what changed is where the
study definition lives and how the measurements are extracted.

SparseArray is now **extraction only**. The task definitions are research
definitions, so they moved here: `inst/settings/studySettings.json`,
`extras/MakeStudySettingsJson.R`, `R/StudySettings.R` and
`R/createOutcomeLabels.R`. `SparseArray::buildCovariateSettings()` is the seam
between the two packages: this package hands it a settings block and gets back
the list of settings objects an extraction needs.

| File | Change | Why |
|---|---|---|
| `inst/sql/sql_server/Inpatient_visit.sql` | `{DEFAULT @restrict_person_table = ''}` and one `AND EXISTS (...)` in the visit occurrence criteria | builds target cohort 1000 from the downstream patients only. Empty renders the definition exactly as before, which `extras/CheckSqlRendering.R` checks both ways, so nothing changes for a run that does not pass a table. Cohort 1003 is derived from 1000's rows, so it needs no change |
| `R/createCohort.R` | new `restrictPersonTable = NULL` argument, passed only to definitions that declare the parameter | the argument the above needs, with no effect on the other 37 definitions |
| `R/StudySettings.R` (now this package's) | `studyExtractionGroups()` also returns `taskIds` | bug fix: `createOutcomeLabels()` iterates `group$taskIds`, which was never returned, so the labelling loop ran zero times and the function always stopped with "No outcome produced any labels" |
| `DockerImage/Dockerfile` | installs `PatientLevelPrediction` | `DESCRIPTION` Imports it, so `R CMD INSTALL` could not succeed without it |
| `R/MeasurementValueUnit.R`, `inst/sql/sql_server/MeasurementValueUnit.sql`, `inst/sql/sql_server/MeasurementValueUnitRef.sql` | the measurements are extracted by this package's own analyses, **998** `MeasurementValueUnit` and **999** `MeasurementNoValue`, with FeatureExtraction's id arithmetic | FeatureExtraction 3.2.0 cannot extract measurement values in a temporal sequence at all: the temporal sequence branch of its `MeasurementValue.sql` has no comma after `as time_id`, so the rendered SQL does not parse. 998 also reads the unit as `COALESCE(unit_concept_id, 0)`, so a numeric measurement with no unit is kept rather than dropped, and 999 covers the measurements with no numeric value, only where 998 produced nothing for the same row, concept and day. `useMeasurement` (701) must stay off or one record would get two covariates |
| `R/extractPlpData.R` (was `R/createPlpData.R`), `R/Settings.R`, and the deletion of `R/Main.R`, `R/StudySettings.R`, `R/createOutcomeLabels.R`, `inst/settings/studySettings.json`, `extras/MakeStudySettingsJson.R` | extraction only: one extraction per call, taking `targetId`, `outcomeIds` and `covariateSettings` instead of reading a study settings file, plus the new `buildCovariateSettings()` seam | the task definitions are research definitions and belong to the study package, which is this one |
| `R/createLongFormat.R` | `covariateRef.csv` gains `unitConceptId` | the covariate id keeps the unit only modulo 1000, and the quantile table is keyed on the whole unit |

`man/createCohorts.Rd` and `man/studyExtractionGroups.Rd` were updated to match.
`codes/`, a 21 MB reference CSV used only by `extras/MakeIcd10CcsrCsv.R`, was not
copied; its output `icd10ccsr.csv` is already in the repository.

`SparseArray::execute()` is not used: it has no `vocabularyDatabaseSchema`
argument, so a site whose vocabulary lives in its own schema cannot be expressed
through it. The stages are called directly instead.

## Checks that need no database

```bash
Rscript extras/CheckSqlRendering.R    # renders and translates all 33 SQL files per dialect
Rscript extras/CheckSqlParameters.R   # every R call site against its SQL file's parameters
Rscript -e 'testthat::test_local()'   # or: R CMD check .
python extras/MakePandasFixtures.py   # regenerate the fixtures from pandas
```

`CheckSqlRendering.R` fails on an unresolved `@parameter`, an unresolved
conditional, or a construct SqlRender v1.9.0 leaves untranslated. It also
renders `Inpatient_visit.sql` with and without the restriction and asserts the
`WHERE EXISTS` appears only with it.

`CheckSqlParameters.R` parses the R code, finds every SQL call site, and
compares the parameters it passes against the ones its file uses. It is what
catches a renamed parameter that only one side knows about.

The tests compare the port against fixtures produced by running the actual
pandas and `bisect` code of the original:

- the quantile boundaries agree with `Series.quantile()` bit for bit, including
  the `q * 100 / 100` round trip pandas does internally
- the bin formula agrees with `max(0, bisect_left(q, value) - 1)` for 197 probe
  values, repeated boundaries included
- the split is deterministic, covers every patient once, keeps 19 digit ids
  intact, is locale independent, and never puts a downstream patient in
  pretraining

## Matching the two sides

`allrecords.csv` identifies a record by `concept_id`, and a measurement by
`"<concept_id>_<bin>"`, because that is what the pretrained embedding is keyed
on: its index is a list of OMOP concept ids, and the model vocabulary is built
from this very column. `featureExtractionLong.csv` identifies a feature by
`covariateId`, which FeatureExtraction v3.2.0 builds as

```
DomainConcept.sql     covariate_id = concept_id * 1000 + analysis_id
                      analysis 101 condition, 301 drug, 501 procedure
MeasurementValue.sql  covariate_id = measurement_concept_id * 1000000
                                   + (unit_concept_id % 1000) * 1000
                                   + analysis_id        (702, temporal set)
                      covariate_value = value_as_number
```

Neither side changes its identifier. Instead the measurement extraction is
aligned to FeatureExtraction, and the conversion is two joins:

```
featureExtractionLong.csv   covariateId, covariateValue
         |  covariateRef.csv, on covariateId
         v
conceptId, unitConceptId    <- named, not computed
         |  meas_quantiles.csv, on (measurement_concept_id, unit_concept_id)
         v
quantile_0 .. quantile_10 -> bin -> "<conceptId>_<bin>"
```

Neither join uses the id arithmetic above, and in particular neither uses
`unit_concept_id % 1000`: `covariateRef.csv` names the concept, and names the
unit in the `unitConceptId` column SparseArray joins in from
`measurementValueUnitRef.csv`. One call does it:

```r
quantiles <- read.csv("output/mimic/meas_quantiles.csv")
long <- read.csv("output/mimic/longFormat/target1000_admission/featureExtractionLong.csv")
ref <- read.csv("output/mimic/longFormat/target1000_admission/covariateRef.csv")

tokens <- covariateToToken(long$covariateId, long$covariateValue, quantiles,
                           covariateRef = ref)
tokens$token      # "316139", "3004501_7", ...
tokens$hasBin     # FALSE where the pair has no quantile row
```

A covariate id that is not in `covariateRef.csv` is an error rather than an
`NA` token: the two files have to be from one extraction.

Three alignments make that work, each recorded in
[OPEN_QUESTIONS.md](OPEN_QUESTIONS.md): the concept filter is
FeatureExtraction's (`concept_id <> 0` and nothing else), the value comes from
`value_as_number`, and the quantile table is keyed on
`(measurement_concept_id, unit_concept_id)`. The one remaining difference is
time resolution: `allrecords` keeps one measurement per hour,
FeatureExtraction keeps the last value per day.

The covariate id carries the unit only as `unit_concept_id % 1000`, so the
whole unit comes from `covariateRef.csv` rather than from the id, and the
residue is never used as a key anywhere: it would be one that is right only
while no two units in use agree in their last three digits. Where two of them
do, FeatureExtraction has merged them into one covariate whose values mix both
units, and that shows up in the conversion itself as `unitAmbiguous`.

### The measurement value covariates

FeatureExtraction 3.2.0 cannot extract measurement values in a temporal
sequence. The temporal sequence branch of its `MeasurementValue.sql` reads

```
FLOOR(DATEDIFF(@time_part, measurement_date, cohort.cohort_start_date)*1.0/@time_interval ) as time_id
ROW_NUMBER() OVER (...) AS rn,
```

with no comma after `as time_id`, so the rendered SQL is not valid SQL. The
analysis is `isDefault = FALSE` in `PrespecTemporalAnalyses.csv`, which is
presumably why the defect survived. So the study settings ask for
`useMeasurementValueUnit` instead of `useMeasurementValue`, and
`SparseArray::createMeasurementValueUnitCovariateSettings()` supplies the SQL:
a copy of FeatureExtraction's file with the comma, which means the covariate
ids and the values are the ones a working FeatureExtraction would have
produced, down to the inherited behaviour that a record with no unit is
dropped and that one concept measured in two units inside one interval
contributes one row.

Keeping those ids means the unit is still only `unit_concept_id % 1000` inside
them, and `covariateRef` has no column for the unit. The column cannot be added
by the builder either: FeatureExtraction merges the results of several settings
objects with `Andromeda::appendToTable()`, which selects the columns of the
table being appended to, `select(data, all_of(colnames(tbl)))`, so an extra
column is dropped on the way in. So the pair is recovered from the CDM, where
the id came from in the first place: `exportMeasurementValueUnitRef()` writes
`measurementValueUnitRef.csv`, the `(covariateId, conceptId, unitConceptId,
recordCount)` crosswalk, and `createLongFormat()` joins its `unitConceptId`
into `covariateRef.csv`. Pass that file to `covariateToToken()` and the
quantile lookup is keyed on the whole unit:

```r
long <- read.csv("output/mimic/longFormat/target1000_admission/featureExtractionLong.csv")
ref <- read.csv("output/mimic/longFormat/target1000_admission/covariateRef.csv")
quantiles <- read.csv("output/mimic/meas_quantiles.csv")

tokens <- covariateToToken(long$covariateId, long$covariateValue, quantiles,
                           covariateRef = ref)
```

A covariate id that two units share, because their concept ids agree modulo
1000, has two rows in the crosswalk. Its values really do mix both units and
no table can undo that, so `resolveCovariateId()` reports `unitAmbiguous`
rather than picking one, and such a row falls back to the bare concept token.
Counting those rows is how you find out whether the database has the problem
at all.

The first sample run has to confirm two things that cannot be checked without a
database: that the builder's `rowId` values line up with `outcomeLabels.csv`,
and that the columns of its three tables match FeatureExtraction's own, since
`appendToTable()` requires the names to agree. Both are a clean failure, not a
silent one: `appendToTable()` matches by name, so a mismatch is an error rather
than a misaligned column.

## person_id

The MIMIC OMOP `person_id` is a hashed BIGINT: 19 digits, sometimes negative. R
has no 64 bit integer, so as a double it silently loses its last digits. The
rule is therefore: joins stay in SQL, anything leaving the database is
`CAST(person_id AS VARCHAR(20))` and is character in R, anything going back in
is inserted as text and cast to BIGINT in SQL.

`checkDatabase()` reports whether this DatabaseConnector keeps a BIGINT intact
and whether rounding ids to doubles would merge two patients.
`runDiagnostics()` compares `person_split.csv` against the database table row by
row, and checks every labelled `subjectId` against the downstream set, which is
where a loss of digits inside PLP would show up.

## Porting notes

The SQL reproduces several accidents of the pandas original on purpose, because
the point is the same records, not tidier ones: a numeric measurement with no
mapped unit disappears, a missing `measurement_datetime` is not filled from
`measurement_date`, and a drug exposure with no end date is dropped. All of them
are listed with evidence in [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md) section C,
and all were confirmed by running pandas rather than by reading it.

The quantile basis is the original's too: every patient, computed before the
split, and recomputed per site. That matters beyond fidelity. Because the basis
and the rows being binned are then the same set, no value can exceed the top
boundary, so the bin stays in 0 to 9 and the token space matches both MedRep's
representation table and the deploy_LG embedding, neither of which has a `_10`
entry. `createQuantileSettings()` can restrict the basis to the pretraining
patients instead, at the cost of letting `_10` occur.

`DATEPART` and `DATEDIFF(HOUR)`, which SqlRender v1.9.0 does not translate, are
avoided by taking the hour of day from [R/Dialects.R](R/Dialects.R) per dialect,
so the SQL is portable beyond SQL Server. Add a dialect there and
`extras/CheckSqlRendering.R` will say whether anything else needs attention.
